# Montages recognized here, and the electrodes they share: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** wl.works sends each probe's positions with `PUT /positions`. This host places them between runs, derives
the montages (one position and one channel selection per probe) and the shared groups (electrodes kept at one position
across montages), and lists both in `GET /sessions`. A canonical names a listed montage and a new `shared` request
names a listed group. Each file's probe joins the insertion that held over the file's montage, so a moved probe is no
longer `unknown`.

**Architecture:** The derivation is pure: `wl_preproc/montage/edges.py` places a position's edges, `derive.py` cuts
montages, `groups.py` finds the shared groups. Each is tested on plain data with exact values. One daemon stage,
`montage/stage.py`, reads the stored positions, runs, census and t = 0, derives, and writes `core` rows. It does this
until the session's first accepted request, then never again. Everything else reads the stored rows through
`montage/stored.py`: the listing, `accept()`, the NWB build and `ephys.link_insertions`. `PUT /positions` stores what
arrives (`request.PositionSet`) and derives nothing.

**Tech Stack:** Python 3.11/3.13, pydantic 2, DataJoint 2 on MySQL (testcontainer), pynwb.

**Spec:** `docs/superpowers/specs/2026-11-24-montages-design.md` at `00c617d` (approved 2026-11-24; amended the same
day from wl.works' review, `f47e73a`, and by the coordinator's placement ruling, `00c617d`). The spec is binding. Where this plan decides something the spec leaves open, the decision
is named `D1`-`D18` below and cited where it is used.

## Decisions on what the spec leaves to the builder (§7) or does not say

- **D1. Where positions live.** `request.PositionSet` (one row per session: `positions_seq`, `received_at`) with part
  `Position` (keyed on `insertion_number`). They sit in `schema/request.py`, the request side.
  - Contract models `PositionsRequest`, `ProbePosition` and `PositionsResponse` go in `contracts/protocol.py`.
  - The schema file is `docs/schemas/positions_request.json`.
- **D2. `PUT /positions` answers.**
  - `200 {"positions_seq", "changed"}`, both for a set it stores and for a no-op.
  - `409 {"error", "positions_seq"}` (the stored seq) for every positions conflict. After the first request, the
    message names that request's idempotency key.
  - `404 {"error"}` for a session that has not landed. `422` for a malformed body, `408` and `500` as on every route.
  - After the first accepted request, a *higher* seq with the *same* set records the seq alone (`changed: false`).
    Otherwise the listed seq would stay behind wl.works' seq for good, and O2's Confirm gate would refuse that
    session.
- **D3. Placing an edge** is wl.works' `place()` kept exactly (spec §4.2 at `00c617d`; wl-works `75c78af5`,
  `src/features/recording/montage.ts`). The window is `[t - tol, t + span + tol)`, with span from D5 and tol 60 s
  only when `t0_source == "manifest"`.
  - *Inside:* the window lies wholly inside one run.
  - *Placed:* otherwise, it touches exactly one gap, even where it also overlaps a run's start or end.
  - *Ambiguous:* it touches more than one gap and none is named.
  - It touches no gap and no run holds it whole (only overlapping runs can do this): inside the first run it
    overlaps, as in wl.works.
- **D4. Naming a gap.** `*_after_run: N` names the gap after run N, and `0` names the gap before the first run. A
  name chooses only among the gaps the window touches; the window alone still decides which those are.
  - A named gap the window does not touch, including any name on a window wholly inside a run, is
    `position_edge_ambiguous` and never trusted. So is a run number that is not a measured run.
- **D5. Precision.** A time whose second and microsecond are both 0 stands for `[m, m + 60 s)`. Any other time is
  truncated to its second and stands for `[s, s + 1 s)`. Positions are stored as `datetime(6)`, so `09:06:00.5`
  never becomes a whole minute.
- **D6. A run's selection.** A run's selection for a serial is the `electrode_config_hash` of the first and the last
  SpikeGLX segment (by start) that overlaps the run and places that serial's sites.
  - Between runs, the earlier run's last selection is compared with the next run's first.
  - A run whose first and last differ has had its selection changed inside it.
- **D7. What the derivation waits for** (`waiting`):
  - stored positions;
  - a stored `ClockReference`;
  - a complete SpikeGLX census: a `SystemTimebase` row for `spikeglx`, every SpikeGLX `core.Segment` censused, and
    at least one Segment or RejectedSegment, or fit status `no_recording`;
  - at least one run that does not end before it starts.
  - A session counts as having ephys when it has a `core.AcquisitionSystem` row for `spikeglx` or `rhs`. Without
    ephys it is `not_needed`, with one montage over all its runs.
- **D8. The stage and its order.**
  - `montage/stage.py::run_stage` runs in `daemon.run_once` after the computed-tables loop (census, `ClockReference`)
    and before `_link_stage`. So the link stage, the listing stage and the NWB stages read this pass's rows.
  - It derives every listable session (`listing.stage.listable()`) that has no accepted request, and rewrites that
    session's rows only when the result differs.
  - A session with an accepted request (`request.first_accepted_request`) is never derived again: its positions are
    frozen (§4.1), and its runs and census do not change once landed. This is how §5's "refused, never applied
    quietly" holds.
  - Montages are numbered 1, 2, … by first run. Groups are numbered by (insertion_number, serial, first montage,
    more montages first, montage ids).
- **D9. The stored rows,** all in `core`, which cannot reference `ephys`, so hashes are soft references:
  - `MontageDerivation` (+`Flag`), `MontageProbe`, `MontageSortableRun`, `PlacedPosition` and `SharedGroup`
    (+`Member`, +`SortableRun`).
  - A montage's runs are not stored: they are the runs whose start lies in its `[start_s, end_s)`, the rule
    `_check_runs` already applies.
- **D10. A serial the census never names** is a probe this host reads no channel map for, whatever the session's
  systems (an Intan probe, or a typo). It bounds montages through its positions. It is listed with
  `electrode_config_hash` and group `electrodes` null, and its montage `sortable_runs` are the runs its position
  covers less those the edges left out. A typo then shows in the listing, beside `probes`.
- **D11. How a `shared` activation is keyed** (§7):
  - `request.SharedActivation` is keyed (subject, session_datetime, group_id, activation_id), with
    `activation_id` always 0, and has part `ProbeRun`. It sits beside `request.Activation`, which is keyed on a
    montage.
  - One per group, deduped as a canonical is: the same key is a retry, and another key returns the stored one. It
    has no supersede.
  - The Phase 2b sort of it will be a sibling of `ephys.Clustering`, keyed on it. Its one effective `ElectrodeConfig`
    is the group's minted intersection, and its key names the group, over which unit identity holds. That sibling is
    not declared here.
- **D12. A `shared` request's runs** are named in `selection.probe_runs`, for the group's one probe. Each run must be
  among the group's sortable runs. It must also be asserted in `metadata.runs` or before, the derivative's rule.
- **D13. The listed seq.** `positions_seq` is the seq the stored derivation was made from, whatever its status. So
  wl.works sees its seq taken in while the session is `waiting` or `ambiguous`.
  - Without a stored derivation (a session not yet passed), `positions_status` is `waiting` and `positions_seq` is
    null.
  - `montages` and `shared_groups` are listed only at `placed` or `not_needed`.
- **D14. Probes in requests.** With positions stored, each `metadata.probes` entry must name a stored position with the
  same serial and insertion number (a 422).
  - A canonical's `probe_runs` for a serial that holds no position in the montage must be empty (a 422).
  - A derivative whose run set holds a run not sortable for a named probe is a 422, never quietly narrowed.
  - With no positions stored (a session with no ephys), probes are recorded as today.
- **D15. Placements that cannot both hold** are flagged `position_edge_ambiguous` and list no montage: a position that
  ends before it starts, or two positions of one serial that overlap, once their gaps are named or placed. No new flag
  code is added.
- **D16. The canonical file's sentence** (§4.7) is appended to its description and names every group whose montages
  include the file's montage. Only a canonical carries it.
- **D17. When the listing follows a `PUT`.** `PUT /positions` stores only. The next daemon pass derives and lists. The
  listed seq says which set the listed montages come from.
- **D18. Overlapping positions of one serial in wall time** are a 422 at `PUT`. So is a duplicate `insertion_number`,
  an `end_kind` without an `ended_at` (or the reverse), an `ended_after_run` without an `ended_at`, and an `ended_at`
  before its `inserted_at`.

## Review Focus

1. **Aware times.** A `PUT` whose times carry `Z` or `+01:00`, and a retry of the same set written naive, are one set.
   The retry is a no-op `200`, never a `409`, and placement reads the UTC instant. (Task 5.)
2. **Positions before t = 0 or the events stage.** Positions sent as soon as a session lands are `waiting`. They are
   placed on a later pass with no second `PUT`, and the listing then carries them. (Task 6.)
3. **A request from an older listing.** wl.works built a canonical at seq 1, and seq 2 changed the montages before it
   arrived. A montage id that no longer exists is a 422 naming `positions_status`, never a file over the wrong runs.
   A probe whose runs are no longer sortable is a 422 naming the run. (Task 8.)
4. **Positions for a behaviour-only session.** They are stored (`200`, the seq listed) and change nothing. The session
   stays `not_needed` with its one montage. (Task 6.)
5. **Back-to-back runs.** With a zero-width gap, a window spanning the boundary is placed in that gap, between the
   two runs. A window that starts on the boundary second lies wholly inside the later run, so it is inside that run
   and never in the gap. (Task 2.)

return inside(gap=index(run) + 1, run_number=run.run_number)
